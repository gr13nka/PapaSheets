# Правила эволюции

Что можно и чего нельзя менять, не сломав уже установленное приложение. Общий принцип один:
на телефоне лежит единственный экземпляр рабочего журнала прораба, второй копии нет нигде.
Поэтому любое изменение оценивается не «работает ли оно на чистой установке», а «что случится
на устройстве, где уже есть данные».

## Схема БД

- Любое изменение entity = bump `APP_DATABASE_VERSION` + настоящая `Migration` в `Migrations.ALL`
  + тест в `app/src/androidTest/.../MigrationTest.kt`. Без миграции Room упадёт при первом же
  открытии — и это правильное поведение, лучше явный отказ, чем тихо стёртый журнал.
- `fallbackToDestructiveMigration` запрещён. В релизе это молчаливая потеря данных при первом
  расхождении схемы.
- **DDL в миграции копируется из экспортированной схемы, а не пишется по памяти.** Порядок:
  правим entity → пересобираем проект → берём `createSql` из свежего `app/schemas/.../N.json`,
  подставив имя таблицы вместо `${TABLE_NAME}`. Room сверяет фактическую схему с ожидаемой по
  `identityHash`: расхождение хоть в порядке колонок, хоть в забытом индексе роняет приложение
  при первом запуске после обновления.
- Миграцию по возможности делать аддитивной: худший исход — лишняя неиспользуемая колонка,
  а не потерянная запись. Пересоздание таблицы с данными (`CREATE`/`INSERT SELECT`/`DROP`/`RENAME`
  — так устроена `MIGRATION_2_3`) допустимо, но это дорогой и необратимый шаг; при пересоздании
  надо руками восстановить все индексы и отложить проверку FK через `PRAGMA defer_foreign_keys`
  (`PRAGMA foreign_keys` внутри транзакции Room игнорируется молча).
- **Чистить схему — до выката, не после.** Пока реальных данных нет ни на одном устройстве,
  цена ошибки в миграции равна переустановке. С первым настоящим журналом та же правка
  становится риском ради косметики, то есть практически неоплатной.
- Старые миграции не удаляются и не переписываются. На устройстве может стоять сборка любой
  давности, и путь «с версии 1 сразу до текущей» — такой же рабочий сценарий, как последний шаг.
  Его и проверяет `migrationChain_fromFirstVersionToCurrent_keepsData`.

## Формат бэкапа

- Версии — `BackupManifest.CURRENT_FORMAT_VERSION` и `MIN_SUPPORTED_FORMAT_VERSION`.
- **Читать назад обязаны, вперёд не можем.** Файл версии выше текущей отвергается с внятной
  ошибкой: угадать смысл незнакомых полей нельзя, а испортить импортом данные — можно.
- Всё знание о старых версиях живёт в `BackupUpgrade`, который приводит разобранный файл к
  текущей форме. Выше него — в мапперах, интеракторах, UI — о старых версиях не знают ничего.
  Поля DTO, оставшиеся только ради чтения старых файлов (`BackupRecord.locationCode`/`workText`
  из v1, `BackupData.locationPresets` из v2), помечаются как «только для чтения vN» и не
  участвуют в экспорте.
- **Шаги апгрейда складываются в цепочку, а не выбираются по одному.** `toCurrent` применяет
  подряд все шаги от версии файла до текущей: файл v1 обязан доехать до v3 через v2. Ветка вида
  «если версия не текущая — применить последний шаг» выглядит рабочей ровно до появления второй
  версии формата, после чего самые старые бэкапы становятся нечитаемыми молча. Цепочку проверяет
  `BackupUpgradeTest.v1 archive is upgraded through every step up to the current format` —
  на файле v1, а не на файле предыдущей версии.
- Новые поля DTO добавляются только со значением по умолчанию — иначе разбор файла предыдущей
  версии упадёт на отсутствующем поле.

## Встроенные поля

Идентификаторы встроенных полей («Локация», «Вид работ») — константы в `:exportkit`
(`BuiltInFields`), а не сгенерированные UUID. Поля заводятся двумя независимыми путями:
чистая установка получает их из сида, обновившееся устройство — из миграции. Со случайными id
эти пути разошлись бы, и бэкап с одного устройства положил бы на другом вторую колонку
«Локация». Живут константы в `:exportkit`, потому что нужны и схеме БД, и апгрейду бэкапа;
зависимость `app → exportkit` уже есть, обратной быть не может.

## xlsx

- Порядок элементов внутри `<worksheet>` задан схемой OOXML, а не нашим удобством: перестановка
  ломает открытие файла в Excel. Формат реверс-инжинирен по эталонному файлу заказчика.
- Ширины колонок выводятся из dp через `Widths` — единственное место, где живёт это
  преобразование; в генераторах XML магических чисел быть не должно.
- Существующие тесты формата — побайтовый регресс-гейт. Если тест упал, разбираемся, что
  изменилось в выводе и почему; **ожидания в тестах не подгоняются под новый код**, иначе гейт
  перестаёт что-либо гарантировать.

## Предупреждение пользователю

Бэкап, снятый новой версией приложения, старая прочитать не сможет (вперёд не читаем).
Если есть шанс откатиться на предыдущую сборку — **бэкап нужно снять до обновления**.
